# 个人助手如何通过 IM 联系本人

**设计提案，2026-11-06。** 用户在 Hope 里有一个可以一直聊下去的个人助手对话，从这里找回、创建或指挥其他工作对话。拟议的手机入口是独立的个人助手 IM。即使同在 Telegram，用户也会看到两个联系人：给普通 Hope 机器人发消息，继续普通工作聊天；给个人助手专属机器人发私信，接续自己的长期助手对话。助手记录指令、目标和处理回执，私人收件箱汇总主动提醒。[总体方案](README.md)

## 拟议 IM 试点的使用流程

1. **连接专属机器人。** 用户在已认证的 Hope「个人助手 → 连接 IM」里添加专属 Telegram bot 凭据。Hope 验证平台身份和独占状态，显示机器人名字及一次性配对码。用户在专属私聊提交配对码，回 Hope 比对目标并确认，最后点该私聊里新出现的「启用」按钮。普通 IM 的账号不会出现在这里供选用，原聊天也不会收到引导私信。
2. **选择手机能管什么、能收到什么。** 用户可只允许手机查询某个工作对话；如需主动通知，再为具体订阅选择发送时间和内容等级，预览例句。最低披露选项只发“你关注的事项有一项需要处理”，详情保留在本地。
3. **在 IM 接着办。** 收到通知后，用户引用该消息问“发生了什么”，Hope 通过发送回执定位同一事项，在当前 IM 会话中仅带入获准披露的上下文。输入“暂停这项提醒”或点对应按钮，Hope 显示该订阅在此渠道的暂停结果。无引用且多项可能匹配时，先列出该用户有权看到的简短选项。
4. **回到桌面查看或撤回。** 收件箱展示触发原因、来源、是否尝试投递和可用的回执。撤销配对让待发、延后和待确认操作立即失效。已提交给平台的消息可能仍到达，状态据实显示；若要删除平台上的已有副本，需遵循相应平台能力及单次操作授权。

## 从本人私聊指挥工作对话（拟议）

配对后，主人为专属私聊选择可操作的工作对话或项目，以及允许查状态、创建、提问、暂停的范围。专属收件器核验身份后把指令提交到同一个长期助手对话，桌面与手机同时发来的指令按该对话 FIFO 排序。仅操作目标工作对话的那一步进入目标自己的队列或停止入口。全程不创建、读取或改变普通 IM 的 `channel_conversations` 挂接行，不执行 `/session` 接管，也不将助手原文写入普通工作对话。[普通 IM 的关联契约](../../architecture/integration/im-channel.md#会话映射与-11-attach) · [跨会话执行入口](../../../crates/ha-core/src/tools/sessions.rs)

| 主人在私聊里说 | 助手如何处理 |
| --- | --- |
| “找到昨天的发布核对，问它还有什么没验” | 在准许的范围内按标题、项目和时间定位。多个匹配先让本人选择；选定后记住目标会话 ID，以此提交一次提问。回给手机的是获准披露的答复摘要及回执，桌面可打开原对话 |
| “另开一个对话检查英文说明” | 复核该项目的创建权限，实际创建成功后返回可再引用的工作对话；重复投递同一条 IM 消息只创建一次。后续“进展呢”在此入口按上次明确目标解释，目标失效或有歧义时重新选择 |
| “先停下刚才那个检查” | 显示目标并按其当前运行身份停止该轮；若用户指的是暂停 Goal、Loop 或提醒，使用对应控制面。目标在确认前已经换轮或结算时报告现状，不把停止请求转给新一轮 |

**当场指令与无人值守委托分开授权。** “现在问它一次”仅授权当下这一步，与目标会话自身权限、审批及当前接收方可见范围取交集。新建工作对话不会自动把整个项目历史开放给 IM。要“每天替我问、变化了发到手机”，须另行明确跟踪来源、时间、预算、收件人和停止条件。已配对私聊、一次操作成功或授权接收提醒，都不能自动扩大其中任何一项。

**“办完告诉我”可以是一次性回报。** 主人在有权限的专属私聊说“查发布进度，办完回这里”，受理时只给该请求绑定一次最终回报，范围沿用当前许可。工作稍后完成，主对话立即更新；发到手机前重新检查配对、披露级别、有效期与免打扰设置。桌面交办默认回桌面主对话，主人可另选已获准的专属私聊。解绑、撤权、过期或送达结果未知时保留本地状态；其他工作与未来变化均须各有依据。验收时关闭所有长期订阅，分别模拟短答、延迟完成及延迟期间撤权。

**工作对话已有或后来接入普通 IM 时。** 每次派工携带不可由模型改写的来源、允许的目标和回传受众，贯穿目标回合、工具、后台任务、子代理与恢复过程。普通 IM 的实时镜像、接管补发、完成通知、问答、审批和附件/资源链接，都要在各自的发送或读取边界排除该次私人指令及其派生内容，即使工作对话在派工后才接入普通 IM。结果与待确认操作仅回到获准的私人助手表面；普通 IM 也不能从历史回放或附件列表取回原文。若某条路径尚不能保证这一点，助手只提供在 Hope 手动打开目标的入口，指令暂留私人对话，不向目标排队、不抢占旧挂接。[普通 IM 镜像与接管](../../architecture/integration/im-channel.md#gui--im-实时镜像) · [普通 IM 交付器](../../../crates/ha-channel/src/channel/worker/dispatcher.rs)

## 两套 IM 的边界与身份独占

| 边界 | 普通 Hope IM | 个人助手 IM（拟议） |
| --- | --- | --- |
| 配置与对外身份 | 普通 IM 设置、账号、凭据和机器人菜单 | 个人助手内独立配置、专属机器人、凭据引用、命令菜单、启停和健康状态。禁用或删除其中一套不改写另一套配置 |
| 入站与对话 | 普通收件器、斜杠命令和审批回调，按现有 1:1 挂接投递到普通会话 | 专属轮询或独立签名 webhook、游标、去重及回调命名空间，经本人配对和授权直达私人主对话。拒绝的消息就地终止，双方均无转投、邀约或自动接管路径 |
| 出站与回执 | 普通回复、会话镜像、Cron 和上线通知沿现有路由发送 | 指令答复经当次入站身份，主动通知经事项投递许可；两者都用专属凭据和独立发件台账。普通投递器不能选取助手端点，助手也不能借普通 bot 补发 |

**同一平台的主体只能占用一侧。** 所有者保存配置时，先以提交的凭据向受信平台核验机器人主体。首版 Telegram 使用 `getMe().id`；用户名、本地账号 ID、API 地址别名和 Token 文本都不能作为主键。双方共用的占用表只保存平台、实际身份命名空间（适用时含租户）、稳定主体 ID、所属产品和连接配置引用；以跨进程唯一约束原子登记。凭据在各自的安全存储中独立持有。相同凭据不得跨产品挂载，密钥校验和报错均不输出秘密。若其他平台无法无歧义核验主体，先不开放该渠道。[现有账号去重](../../../crates/ha-channel/src/channel/accounts.rs) · [Telegram 身份核验](../../../crates/ha-channel/src/channel/telegram/mod.rs)

两侧的新增、恢复、轮换和连接启动都遵循“只读查询身份 → 原子占用 → 注册菜单、轮询或 webhook”的顺序。普通 IM 历史账号先登记已核实的身份；同平台旧账号的身份仍不明时，阻止新助手连接上线并提示处理。遇到冲突时保留原配置与服务，拒绝新连接。更换 API 代理地址或 Token 不改变同一平台的机器人主体；同名但 ID 不同的两个 bot 可分别使用。

删除 Hope 配置后，Telegram 用户仍可从原联系人继续发信。因此，停用时保留占用；显式移除时先撤销路由、停止收发、清理待发和凭据，再释放活动连接。在同一 Hope 数据根保留最小的机器人主体及历史用途，禁止另一产品认领；改用另一产品须另配 bot。原用途重新添加也须新配对，重新授予收发权限。

可复用的底层包括平台 API 客户端、协议编码、格式化、签名验证、限速和连接重试。普通 Telegram 启动流程在 `getMe` 后同步普通命令；其 `convert_update` 在进入公共事件总线前就会调用普通斜杠命令、审批或问答处理器。专属连接必须在原始 Telegram `Update` 层选择自己的解析器，仅更换下游事件总线无法隔离这些副作用。外部入站不能靠正文、前缀、`chat_id` 或同名用户自行选择产品。[普通 Telegram 启动](../../../crates/ha-channel/src/channel/telegram/mod.rs) · [现有回调分派](../../../crates/ha-channel/src/channel/telegram/polling.rs)

## 本人配对、收件人和权限

建议以四种独立记录裁决以下问题。持久化与授权查验留在 `ha-core` 的类型化接口，渠道适配器仅消费已批准的一次投递。

| 记录 | 证明什么 | 何时失效 |
| --- | --- | --- |
| 本人配对 | 某个 Hope 所有者控制面与指定机器人、远端真人、租户和真实私聊的双向验证。仅保存短期随机配对码的散列，限制尝试次数、有效期和使用次数 | 撤销、删除或重配账号至其他机器人、私聊身份不符。重连同一身份可恢复，无法证明身份相同则要求重新配对 |
| 前台指挥许可 | 绑定主人、专属端点和配对代际，持久记录准许操作的项目或工作对话、动作集合、答复披露等级、有效期与许可修订。允许“只查 A 的进度，手机只看状态”，无需订阅任何提醒 | 查候选、派工或发答复前均复核当前修订及目标权限。可只撤一项目标或动作；配对、其他目标和独立投递许可分别裁决 |
| 投递许可 | 所有者明确允许某订阅把哪种内容发给哪个专属私聊。保存许可版本、准许的来源范围、内容等级、安静时段、有效期和暂停状态 | 变更后旧版本待发项须重新裁决。专属身份或配对变化使旧许可失效 |
| 单项交互与回执 | 绑定事项、订阅版本、允许的动作、专属连接主体、配对版本、私人主对话和远端消息 ID。按钮另用短期不可猜测句柄，一次消费 | 过期、端点换绑、事项已处理、旧版本按钮重放或配对撤销 |

专属收件器在写历史和运行模型之前识别配对操作，避免配对码进入模型输入和日志。在 Telegram 验证平台原始 private 类型及真实 `from` 用户，拒绝缺失、bot 和代发身份。常规 IM allowlist、既有挂接、最近活跃、启动通知开关、群管理员身份或同名联系人，都不能代替本人配对。两侧的配对命令、配对码格式和按钮句柄要可区分；误发到另一产品的配对请求或按钮就地拒绝，不进入聊天历史、日志、模型或转发路径。[现有入站身份类型](../../../crates/ha-core/src/channel/types.rs)

**手机能撤掉哪些权限。** 首版允许已配对本人在专属私聊移除一项目标或动作、暂停当前端点的提醒、降低披露等级或解绑自己。确定性操作写入新版本，排队指令和待发项立即重验。新增或更换连接、扩大可操作的项目或来源、提高披露等级、恢复已暂停的投递或授予新的长期委托，都须回到已认证的 Hope 控制面确认。私聊里的自然语言可生成供主人查看的草稿，不能直接扩大授权。

**无痕与跨来源隔离。** 在发现候选、渲染收件箱、发送和读取回复详情时都要核验当前来源授权及 `sessions.incognito`。无痕来源不得产生订阅、收件箱行、IM 内容或配对关联。经 Cron 产生的结果可能享有所有者上下文，IM 则默认不能读知识库；指令答复和主动外发都只使用来源与接收方获准看到的最小投影，不直接发送原 turn、日志、工具输出、文件路径或本人记忆。若连事项存在本身也无权披露，完全静默。[知识库权限与来源](../../../crates/ha-core/src/knowledge/access.rs) · [无痕契约](../../architecture/core/session.md)

**同一个主对话按接收方组装模型输入。** 手机回合只装入当前端点有权看到的历史片段、事项和工具结果。桌面专属原文及其压缩摘要、记忆、缓存和续跑上下文一并排除；旧摘要缺少来源和受众时，从仍获准的引用重建。按接收方和许可版本隔离派生上下文，撤权后重建。无法证明输入范围时，仅返回允许披露的固定状态，或请本人回 Hope 查看。普通会话按会话 ID 读取的整份上下文不能直接用于该回合。[现有上下文存取](../../../crates/ha-core/src/session/stream_persistence.rs)

**群聊、话题及第二个渠道。** 拟议 IM 试点仅允许一个已验证私聊接收该订阅。群内 @、转发的私聊、复制的操作卡都不能进入本人的助手指挥范围。本人在私聊转来群消息时，转发文本只作为引用材料，只有本人另写的指令可请求动作。未来的群协作使用独立的群订阅和群可见事项。增加第二个 IM 时分别验证人和端点，依各自的许可展示事项、摘要和本次回执；不会自动镜像长期助手、工作对话或另一个渠道的历史原文。收件箱链接在打开时重新鉴权；不把 Owner Token、长期访问票据或凭据放进 URL。

## 哪些渠道可以先做

下表区分**已有适配器行为**和**建议开放顺序**。选择器还须检查已启动的账号、真实会话类型、受支持的正文类型、话题/锚点和回执质量。现有 `ChannelCapabilities` 主要表达回复、线程、媒体和预览能力，缺少“这个目标现在能否无原消息主动发送”的统一判定。建议添加独立的按账号与目标判定，并返回许可、需锚点或能力未验证及原因。[现有能力定义](../../../crates/ha-core/src/channel/types.rs)

| 渠道 | 仓库中现有行为 | 个人助手建议 |
| --- | --- | --- |
| Telegram | 文本 `sendMessage` 按 chat 发，原消息锚点可空，服务响应提供消息 ID。格式化后的文本按一次远端修改处理。[发送实现](../../../crates/ha-channel/src/channel/telegram/api.rs) | 首选已配对、无话题的本人私聊。单条有界纯文本，禁用媒体、链接预览和自动提及对外部人的能力后再开放 |
| 飞书 / Lark | 文本发送支持 chat 或原消息回复，当前普通文本路径只把 `reply_to_message_id` 传给发送层。[适配器](../../../crates/ha-channel/src/channel/feishu/mod.rs) | 第二批可评估已配对私聊。线程寻址未经验证时拒绝，避免发到上一级聊天 |
| Slack、Discord、Google Chat | Slack 的普通消息可用 channel 与可选 thread ts，原生流另有锚点条件。Discord 区分目标与可选回复。Google Chat 用 space 和可选 thread key。[Slack](../../../crates/ha-channel/src/channel/slack/mod.rs) · [Discord](../../../crates/ha-channel/src/channel/discord/mod.rs) · [Google Chat](../../../crates/ha-channel/src/channel/googlechat/mod.rs) | 逐平台核验私聊、线程、权限和平台回执后开放。Slack Connect 要覆盖同用户字段在不同租户下的拒绝用例 |
| 企业微信 | 只允许对本账号、目标和未过期的原消息回调发送最终文本，无锚点发送会被拒绝。[适配器](../../../crates/ha-channel/src/channel/wecom/mod.rs) · [负例](../../../crates/ha-channel/src/channel/wecom/tests.rs) | 目标选择器显示“仅可回复入站消息”。本地收件箱可用，无锚点时发送次数必须为零 |
| 微信、QQ Bot、LINE | 微信发送会查账号与联系人的 context token，QQ 能构造不含被动回复字段的请求，LINE 有 reply token 和 push 两条路径。[微信](../../../crates/ha-channel/src/channel/wechat/mod.rs) · [QQ](../../../crates/ha-channel/src/channel/qqbot/api.rs) · [LINE](../../../crates/ha-channel/src/channel/line/mod.rs) | 需要独立确认真实账号的发送窗口、订阅资格、配额或费用、幂等与回执语义。LINE 将主动通知与入站 reply token 分开，避免消耗另一轮的回复身份 |
| WhatsApp、Signal、iMessage、IRC、自定义插件 | 分别依赖本地桥接与发送前检查、signal-cli、macOS CLI 或 IRC 连接。IRC 在写出后生成本地 UUID。[WhatsApp](../../../crates/ha-channel/src/channel/whatsapp/mod.rs) · [Signal](../../../crates/ha-channel/src/channel/signal/mod.rs) · [iMessage](../../../crates/ha-channel/src/channel/imessage/mod.rs) · [IRC](../../../crates/ha-channel/src/channel/irc/mod.rs) | 默认保持本地收件箱。完成接收人身份、主动发送和可靠回执的逐项验证后，再开放单个平台；本地生成的 ID 不得显示为远端确认 |

平台侧也有两条直接影响首轮体验的约束。Telegram 普通 Bot 不能先与一个陌生用户建立对话，必须由用户先发消息；这正好可以承载一次性配对。之后的 `sendMessage` 成功会返回消息对象，它只证明 Telegram 接受了请求，不能证明主人已读。[Telegram 机器人说明](https://core.telegram.org/bots#how-are-bots-different-from-users) · [sendMessage 协议](https://core.telegram.org/bots/api#sendmessage)。Slack Connect 中，应用会收到外部组织成员的事件，单一字段不足以确认成员来自哪里；不可仅凭频道内可见或显示名承认其为主人。[Slack Connect 的外部成员说明](https://docs.slack.dev/apis/slack-connect/#external-members)

## 投递、取消与恢复

发送一条消息，需要一条能回答“因为什么事项、基于哪次来源变化、允许谁收到”的记录。复用 Primary 所有权、来源去重、按目的地排队等底层机制，专属队列的键要包含产品用途、已核验的机器人身份和配对版本。个人助手单独记录每个收件人每次通知的结果。普通通用发送工具、Cron 目标选择器和后台 fan-out 既不能枚举、也不能按猜测的 ID 使用个人助手账号或收件人；执行层双向验证连接用途，不能只在界面隐藏选项。[普通 Cron 投递](../../../crates/ha-cron/src/cron/delivery.rs) · [IM 进程所有权](../../../crates/ha-core/src/channel_hooks.rs) · [端点发送顺序](../../../crates/ha-channel/src/channel/worker/provider_lane.rs)

| 节点 | 动作与状态 |
| --- | --- |
| 收到变化 | 核对原始来源、事务内按“订阅 + 来源事件版本 + 收件人”去重，写入事项与待发意图。静默条件成立时不访问平台。已向本地展示的事项只更新同一行 |
| 待发 / 延后 | 只有桌面或服务器 Primary 可认领。查最新授权、绑定、渠道状态、来源、内容等级、安静时段、过期时间和打扰预算；安静期内聚合同一事项。恢复时重算是否仍有价值 |
| 准备发送 | 在专属目的地 FIFO 中等待。轮到时再次检查连接用途、平台机器人主体、配对代际、受众与本次回复或主动通知的许可，事务写入不可重放的尝试标记后才允许插件发起单次请求。来源失效、配对撤销或事项已解决时停止；摘要严控为一条消息，转义平台标记并禁用外部预览 |
| 平台结果 | 有可信回执才标“平台已接收”，记录可用的远端消息 ID；RPC 写出、生成本地 ID 和已读是不同事件。用户数小时后未回复也不自动判作已读、马上催办或升级渠道 |
| 失败或崩溃 | 能证明请求尚未提交时，才可在限额和有效期内重排。请求启动后超时、不可判定的 5xx、发送后写回执前崩溃，以及重启发现已标尝试却无回执，一律标“结果未知”，不自动重发。只有具备可靠查询/幂等能力的渠道才可对账。已禁用、过期、权限不足保留本地原因；人工再发须展示可能重复并产生独立尝试 |
| 撤销 / 停止 | 解绑、移除专属连接或更换主体时递增代际，拒绝旧入站、已排队指令、交互句柄、未提交的回复及延后通知；重启仍以新代际裁决。已进入目标执行的工作按原取消语义处理，解绑不擅自停止无关工作。平台已经接收的请求只据实记录回执或“结果未知”，之后不借旧路由、普通 IM 或其他账号补发 |

回执只记录关联键、必要的受限平台标识、状态、尝试时间和脱敏原因。禁止存储原始 webhook、配对码、回调密钥与预览正文副本，删除订阅或历史时按主方案的清理规则处理。已存在的 `InboundEvent::ReadReceipt` 由 dispatcher 记录日志；若未来显示“已读”，先实现按账号、目标、message ID 和接收者验证持久证据。低层 `DeliveryResult::success=false` 本身无法证明未提交。[回执类型](../../../crates/ha-core/src/channel/types.rs) · [入站事件分派](../../../crates/ha-channel/src/channel/worker/dispatcher.rs)

## 专属私聊中的回复与确认

对专属收件器已核准的消息，先匹配真实身份和本产品的动作句柄。配对、暂停及撤销操作来自确定性解析，不交由模型识别，也不能用一条裸“好”授权外部动作。引用通知消息时按专属路由和远端 message ID 查对应事项，重复回调只返回既有结果。无法解析的操作在专属私聊内澄清或拒绝，不能送入普通工作聊天或交给其通用命令处理器。

**积压消息如何分代。** Telegram 试点采用专属顺序轮询。首次或重新配对经过 Hope 确认后，专属 bot 向该私聊发一次性启用按钮；本人点下后，从这条已核验的回调起接收新指令。边界前的积压消息只确认消费，不执行。收件器在同一事务内记录原始事件去重键、处置结果或待执行指令及消费游标，提交后才向平台确认；重启沿同一代际恢复。游标丢失或无法证明事件顺序时回到待启用状态。仅新发的本人消息和本代有效按钮可触发操作，编辑旧消息无论是否产生新的 `update_id` 都不能成为新指令。[现有 Telegram 轮询与编辑消息处理](../../../crates/ha-channel/src/channel/telegram/polling.rs)

Telegram 连续至少一周没有更新时，下一条更新的 ID 可以随机起步。收件器记录最后一次平台更新的时间，在持续轮询和重连时都检查间隔，进入这一窗口前清除旧偏移。连续在线且已消费完毕时沿原配对处理新消息，出现无法对账的断档时才重建启用边界。验收要包含“新一条合法更新的 ID 比一周前更小”，以免旧偏移将其直接确认丢弃。[Telegram Update 协议](https://core.telegram.org/bots/api#update)

对“为什么提醒我”这类需要模型解释的追问，使用 `TurnRequest` 与拟议的个人助手 IM 来源提交，经私人主对话 FIFO 进入 `TurnKernel`。保留连接用途、配对主体与代际、来源和受众；引用文字套不可信信封。若用户接着要求发邮件、改日程或给第三人发消息，沿内核的工具审批逐次裁决；配对、确认收到和延后提醒均不授权该动作。审批必须绑定到当次请求、本人和专属路由，缺少可信交互能力时保留在已认证的 Hope 界面。超时只显示待处理或过期。[内核准入](../../../crates/ha-core/src/chat_engine/turn_kernel.rs) · [权限与审批](../../architecture/agent/permission-system.md)

## 交付验收

| 场景 | 可观察结果 |
| --- | --- |
| 普通 IM 已登记机器人 A。同时在助手配置提交 A 的新 Token、改本地 ID 或改显示名；反向也试一次 | 以平台返回的主体识别为同一个 A，仅原用途可运行。拒绝方零轮询、零命令菜单修改、零 webhook 接管。旧账号的主体未核实时不启动新助手连接 |
| 删除普通机器人 A 后在「个人助手 → 连接 IM」输入它的新凭据；用户同时从原 Telegram 联系人发信 | 历史用途登记拒绝跨产品认领，原联系人消息零助手入站；同名的新机器人 B 可单独配对 |
| 普通机器人 A、助手专属机器人 B 与同一用户各有私聊，数值 chat ID 相同。分别发消息、引用通知、复制按钮或输入对方的命令 | A 只进入普通对话，B 只进入私人主对话；各自用原机器人回复。误投的配对码、审批及跨产品回调没有副作用，历史、未读、按钮和回执不串线。通用发送工具和 Cron 均无法列出或直接选中 B，助手发件器也拒绝 A |
| 私人助手委托的目标此前已挂接普通 IM，或执行中接入普通 IM；目标发出流式输出、提问、审批、附件和晚到的后台结果 | 普通 IM 即时、恢复和历史补发均无私人内容，也没有可用的附件链接。无法约束目标可见性时未提交派工，仅在 Hope 提供手动打开入口，原关联完整保留 |
| 助手有排队指令、延后主动通知和待回复消息时解绑，随后重启、重新配对、重放旧消息与操作卡 | 旧代际入站零执行、未提交消息零外发、不改投普通 IM。已交给平台而尚无回执的项保留未知。新配对仅接受新授权；普通 bot 同期正常收发 |
| 解绑期间给 bot 发“另开一个对话”，让平台积压到重配；启用后编辑旧消息，再新发一次同样的指令 | 积压和编辑均零派工；仅新指令创建一个会话，收件器提交后崩溃重启也不重复创建 |
| 桌面输入仅本地可见的独特测试词并触发压缩，手机追问“刚才说了什么”；随后在手机降低披露等级，再要求恢复或增加项目 | 手机回合的实际模型请求、工具参数和回执都没有测试词，缩小权限立即生效；恢复或扩大范围只引向已认证 Hope，授权记录没有被扩大 |
| 只授权手机查工作对话 A，未订阅任何提醒，重启后查询并尝试暂停 A；再订阅 B 的通知，单独撤销 A 的查询权 | 重启后能查 A、不能停 A。撤权后无法再发现或查询 A，排队中的旧查询与回复均失效；本人配对和已准许的 B 通知仍有效 |
| 同一个已授权来源连续报告相同变化，另一个未订阅的来源也有变化 | 本地为前者产生一个事项，在明确许可的私聊只尝试一次。后者零投递、零披露 |
| 同名账号、另一个 bot、相同 chat 不同线程/租户、缺真实 sender、群内转发配对码、已使用码 | 无法绑定或提交控制动作，不落入模型上下文、日志或群公告 |
| 排队期间撤权、专属连接身份变化、知识库权限关闭、转为无痕、暂停/删除订阅、事项已解决 | 发送前复验拦截尚未开始的请求；零远端写入。无痕源无待发记录、无内容预览 |
| 桌面与服务器并存，发送时休眠或进程重启 | 只由 Primary 认领。无远端副作用的待发可以恢复，过期项本地结算。已交给平台而回执丢失的项只显示“结果未知” |
| 安静时段、额度用完、用户连续忽略 | 本地可查看，IM 无打扰；恢复后最多发仍有价值的合并通知。可见的暂停/静音一直有效 |
| 引用本人通知追问，与桌面输入并发，或复制旧按钮到其他聊天 | 追问排入正确会话、只解释这一事项；旧回调拒绝且不触发模型或工具。另一端处理完成后旧互动关闭 |
| 桌面指定工作对话 A，已授权私聊接续提问；另一渠道转来“暂停 B”，或平台重复投递创建指令 | 助手只关联 A 的实际回执；对话原关联不变，转发内容不能停止 B，重复消息只创建一个工作对话。没有长期委托时不会产生后续定时操作 |
| 企业微信无锚点、飞书未验证线程、未知插件；Telegram 受限账号或回执超时 | 不支持的路由零尝试；不降级到父聊天或另一个账号。模拟平台接受与超时分别检查状态和尝试数 |

离线验收使用临时数据库、假时钟、两个进程身份、模拟适配器与合成事件，检查数据库状态及远端调用次数。配对、投递、引用回复和撤权构成一个完整试点；正式开放给真人前，在自愿提供的测试账号上补做一次完整私聊流程、撤权和真实回执验证。渠道表中其余各项独立验收。
